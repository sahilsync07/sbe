Dual Application Architecture: e-SBE vs e-SBE Hub

System roles, folder organization, Vite code-sharing engine, and functional boundaries

The SBE software infrastructure consists of two distinct applications operating off a unified, single source of business truth. Understanding their distinct missions and shared engine is essential for every developer and AI agent working in this repository:

e-SBE (Client App)

Catalog • Showroom • Quick Ordering
Target: Buyers & Staff
Dir: frontend/ History: Web (HTML5) / Hash (Android) Capacitor: com.sbe.app

High-performance, touch-first digital footwear showroom designed for counter retail clients, wholesale store buyers, and field sales reps.

e-SBE Hub (Operations)

Back-Office • Ledger Analytics • Management

AI Master Commandments & Onboarding Rules

Strict instructions that every AI assistant and human engineer MUST follow in this repository

Commandment 1

Android Build: Always Use npm run build:android

When building assets for Capacitor Android, NEVER run standard npm run build. The standard build sets base: '/sbe/' for GitHub Pages, which will cause a blank white screen on Android devices! Always run npm run build:android, which sets base: './'.

Commandment 2

CSS Isolation: No Naked Element Selectors

NEVER declare global element selectors (such as button { ... }, input { ... }) in frontend/src/style.css or component roots. They bleed uncontrollably into mobile headers, icon buttons, and toolbars, causing unwanted blue fills and broken layouts. Always use scoped styles or explicit class names.

Commandment 3

Tally Sync: Never Wipe Custom Metadata

Fresh Tally ledger exports contain only raw accounting balances and transactions. They lack custom application tags (partyType, creditStatus, settlementStatus, settlementNote, settledAmount). Any code updating ledger-data.json must merge existing tags in memory before writing to disk.

Commandment 4

Multi-Repo Mirroring: Keep Git Trees in Sync

The project is mirrored across two local repositories: c:\Projects\sbe and C:\Projects\sriyasync_github\sbe. Whenever making commits and pushing to remote, both repositories must be updated and kept in strict lockstep to prevent diverged heads.

Commandment 5

Batch Commit Pattern: Zero Commit Flooding

Do NOT create an individual Git commit or backend write for every single item tagged or photo uploaded. All operations (Party Tagger, Sample Room, Photo Uploads) must buffer changes in a reactive staging store, display a Commit Preview counter, and commit all changes in one single batch commit.

Commandment 6

Single Source of Truth: Edit in frontend/src

Because sbe-hub falls back to frontend/src/ via Vite, all shared components, composables, and utility functions should be modified in frontend/src/. Do not duplicate code into sbe-hub/src/ unless creating a Hub-exclusive page or override.

Commandment 7

Canvas Rendering: Preserve Aspect Ratio

In One-Touch Mode and social card generators, footwear photos come in varying proportions. NEVER stretch or squeeze image dimensions to fit fixed canvas boundaries. Always compute proportional scaling and letterbox/center the photo cleanly on the canvas.

Commandment 8

Visual Integrity: Zero AI Mockups or Clip-Art

Absolute zero tolerance for AI-generated logos, clip-art shoes, or cartoon banners. Only use authentic manufacturer brand logos extracted from official vector catalogs or high-resolution physical scans (Paragon, Eeken, Action, Cubix, Swastik).

The Golden Rules & Image Architectural Commandments

Strict operational guidelines governing image selection, filtering, and customer presentation

Zero Tolerance

Rule 1: Strict Negative Content Filter

Under NO circumstance may any marketing card include:
• Top Banner Text: "Sri Brundabana Enterprises", "SBE Rayagada", or daily stock dates.
• Bottom Footer Text: "Qty", "Qty:", or isolated carton piece counts.
Rationale: Wholesale buyers must see manufacturer-authentic promotional assets. Internal warehouse stock story cards reveal confidential counts and look unpolished.

4-Stage Pact

Rule 2: Catalog Card Synthesis

When using raw catalog PDF cutouts, follow the exact 4-stage compositor pipeline:
1. Crop out footwear product tightly.
2. Remove solid or messy background cleanly.
3. Upscale & HD enhance contrast and clarity.
4. Composite onto branded wave background with top-right logo, drop shadow, and bottom specs strip.

Cloud Standard

Rule 3: Semantic Asset Naming

Never upload cryptic WhatsApp filenames (e.g. IMG-20240807-WA0013.jpg). All Cloudinary assets must be normalized to:
[BRAND]_[MODEL]_[COLOR].jpg
Examples: RELIANCE_XM_9021_NVY.jpg, ACTION_AXEL_BLK_WHT.jpg, CUBIX_50251_GRAP.jpg, EEKEN_2141_BRT.jpg.

Priority Hierarchy

Rule 4: Manufacturer Precedence

Whenever clean manufacturer promotional cards are available in Quick Share / WhatsApp archives (and pass all negative filter checks), they must be strictly preferred over catalog cropped cutouts. Real factory cards contain authentic color grading and typography.

Visual Integrity

Rule 5: Zero AI-Generated Brand Assets

Absolute purge of AI-designed clip art (shoe-prints, cartoon icons, gradient SVG mockups). Use only authentic manufacturer brand logos extracted directly from official physical catalogs or high-res vector scans (Paragon, Eeken, Action, Solea, Paralite, Comfy).

Brand Boundary Isolation

Rule 6: Cross-Brand Matching Prohibition

Models must strictly match within their brand boundary. An Eeken product name ending in MRP1449/- must never match a Paragon EV1449LP slipper. Price tokens (MRP..., RS..., @...) must be stripped before model tokens are evaluated.

Party Tagger & Risk Analytics Engine

Customer classification, Bad Debt flagging, Settled account monitoring, and Criticality aging

Built directly into e-SBE Hub (route /party-tagger), this module equips management to segment customers and track default risk across thousands of Tally ledgers without modifying Tally's core chart of accounts:

Classification

Wholesalers vs Retailers (partyType)

Differentiates wholesale volume buyers from retail counter customers. Essential for margin analysis, targeted price tiering, and specialized promotional broadcasts.

Credit Risk

Credit Risk Flagging (creditStatus)

Three operational states: Normal (healthy credit), Doubtful 🟠 (payment delayed/unresponsive), and Bad Debt 🔴 (written off / uncollectable). Bad debt balances are automatically isolated and deducted in financial dashboards.

Settlement

Settled (Not Accounted) (settlementStatus)

Tracks accounts where a physical settlement or compromise agreement was reached but not yet passed in Tally by the accountant. Captures settledAmount and settlementNote.

Data Pipeline & Tally Metadata Preservation Lock

Tally XML ODBC integration, dual-path asset disk persistence, and in-memory metadata lock

The local backend (backend/src/server.js) interfaces with Tally Prime and Tally ERP 9 over XML port 9000. It features a critical safeguard: the In-Memory Metadata Preservation Engine.

The Problem It Solves: In Tally, custom tags like partyType: 'wholesaler', creditStatus: 'bad_debt', or settlementStatus: 'settled_not_accounted' do not exist. Whenever Tally synchronizes, an unshielded export would wipe out all party classifications and settlement notes!
The Architectural Solution (syncLedgerToFile): Before writing freshly parsed Tally ledgers to disk, the server reads the current ledger-data.json into memory. It builds a case-insensitive dictionary of all tagged parties keyed by ledgerName.toLowerCase().trim(). When fresh financial figures are parsed, each ledger record is re-attached with its preserved custom tags. Custom party tags and sample room flags are permanently locked and preserved against Tally overwrites!

Direct Dual-Path GitHub Synchronization Engine

Local backend priority with automatic direct GitHub API fallback for remote & mobile users

Engineered in frontend/src/utils/githubSync.js, the syncDataDualPath() utility guarantees that updates succeed whether the user is on the warehouse desktop or a mobile phone on a remote sales trip:

Step 1: Local Backend
Attempts local Node server endpoint (e.g. http://localhost:3000/api/...) with a strict 2500ms timeout.
Step 2: GitHub API Fallback
If backend is offline or timed out, falls back to direct GitHub REST API using authenticated Personal Access Token.
Step 3: Conflict Resolution
Fetches latest file SHA, base64 encodes data, and automatically retries upon HTTP 409 commit collisions.
Step 4: Live Cache Refresh
Flushes local cache and emits reactive updates across UI composables without requiring a page reload.

One Touch Mode & HTML5 Canvas Compositor

Natural aspect ratio preservation, pure black bottom extension bars, and royal gold cover synthesis

Aspect Ratio Rule

Natural Aspect Ratio Preservation (Zero Squashing)

Footwear manufacturer promotional cards often have tall portrait dimensions. Previously, forced scaling stretched or compressed photos unnaturally. The compositor now calculates proportional scaling:
scale = Math.min(canvasWidth / img.width, canvasHeight / img.height)
The photo is centered and letterboxed within a clean 4:3 frame without a single pixel of distortion!

The 4-Layer Defense Engine

Multi-stage image verification pipeline executing in process_all_quick_share.py

Layer 1: Aspect Ratio
Rejects full-screen phone screenshots (ratio < 0.58). Saves hundreds of OCR cycles on non-product images.
Layer 2: Visual Strip Scan
Samples top 8% and bottom 8% pixels. Rejects images with solid black status banner overlays (brightness < 35).
Layer 3: Fuzzy OCR Rejection
Scans for dealer names (Rayagada, Brundabana, SBE) with Levenshtein typo tolerances and WhatsApp date stamps.
Layer 4: Footer Qty Scanner
Examines bottom 15% for inventory count badges ("Qty: 12", "Qty 48"), preserving manufacturer purity.
